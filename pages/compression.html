03 · Compression

P.E.L.I.C.A.N.

Perceptual Edge Lightweight Intelligent Compression and Adaptive Network — the C++ half of the project, written by Shreyash Thakur. The premise is that within a ten-second clip the frames are not equally worth keeping, so quality should track content rather than being fixed once at encode time.

What happens to an event

The engine runs a producer/consumer split. main.cpp polls shared memory and pushes event windows onto a queue; a worker thread pulls them off one at a time and runs the pipeline below. Because it is a queue, an event arriving mid-encode waits rather than being lost.

1
Cluster EventCluster decides whether this event should be merged with the previous one, and ranks whatever comes out by priority.
▾
2
Read For each index in the window, the JPEG is read from the ring and decoded, with a guard against reading slots the writer has not filled yet.
▾
3
Score ImportanceEngine reduces the frame to a single number in [0, 1] from five weighted signals.
▾
4
Govern SystemGovernor reports how loaded and how hot the Pi is; that pressure pulls the score down and the CRF up.
▾
5
Encode H264Encoder writes raw BGR down a pipe to FFmpeg, using the Pi's hardware encoder where it exists.

Importance scoring

Analysis runs on a 320×180 copy of the frame while the encoder works at 640×360. Halving the analysis resolution is nearly free in accuracy terms — edge density and mean absolute difference are both aggregate statistics — and it cuts the per-frame cost by a factor of four.

SignalWeightHow it is computed
Motion0.30 Mean absolute difference against the previous frame, normalised to [0, 1], EMA-smoothed 0.7 prev / 0.3 new, with anything below 0.015 zeroed as sensor noise
Spatial0.20 Canny edge density (thresholds 50/150) across the whole frame
Region0.20 Edge density inside the centre half of the frame, scaled 1.35× and clamped
Temporal0.20 Gaussian falloff from the event midpoint: exp(-d² / 80)
Face0.10 Haar cascade run every 10th frame; score is the largest face area over 18% of the frame, decaying 0.85× on frames where no face is found

Why each one is there

  • Motion is the primary signal, and the EMA is what stops quality oscillating frame to frame. A single-frame spike moves the smoothed value by only 30% of its size.
  • Spatial edge density stands in for detail. A frame full of edges loses more visible information per unit of compression than a flat one.
  • Region encodes the assumption that the subject is roughly centred. The 1.35× scaling makes the centre count for more than its area alone would give it.
  • Temporal is a prior, not a measurement. The detector padded the window by five seconds each way, so the middle of the clip is where the incident probably is. The Gaussian is narrow — at 20 frames from the peak it has already fallen to essentially zero.
  • Face is deliberately the smallest weight. It is a presence detector, not identification, and running it every tenth frame with a decay between hits keeps the cascade off the critical path.

The log curve

The weighted sum is not used directly. It is passed through a logarithmic normaliser: 

float raw = 0.30f * s.motion
          + 0.20f * s.spatial
          + 0.20f * s.region
          + 0.20f * s.temporal
          + 0.10f * s.face;

float normalized = std::log1p(raw * 7.0f) / std::log1p(7.0f);
s.score = std::clamp(normalized, 0.0f, 1.0f);

This exists because raw scores cluster near the bottom of the range. Mean absolute difference on a 320×180 frame is a small number even during obvious movement, and a linear map would push nearly every frame into the lowest quality tier — which is a fixed-CRF encoder with extra steps. The curve lifts the low end so the tiers actually get used, and it does so smoothly rather than by rescaling around a hand-picked midpoint.

System pressure

The compressor shares four cores with five Python processes, and it is the only one that can afford to back off. SystemGovernor gives it the information to do so. 

float cpu     = getCpuLoad();      // delta of idle vs total from /proc/stat
float thermal = getThermalLoad(); // thermal_zone0 temp, normalised against 100 °C

float pressure = std::clamp(0.7f * cpu + 0.3f * thermal, 0.0f, 1.0f);

Pressure feeds the pipeline in two places. It scales the fused importance down by up to 25%, and it is added directly to the CRF at up to six points. The same scene therefore encodes more cheaply on a hot, loaded Pi than on a cold idle one, without any explicit throttle logic.

Dropping frames

A dropped frame is unrecoverable, so the engine makes it hard to happen. Three independent conditions must all agree:

  1. Policy. CompressionPolicy::shouldSkipFrame returns false outright below 0.75 pressure. Between 0.75 and 0.9 it will skip frames scoring under 0.3; above 0.9, frames under 0.5.
  2. Continuity protection. The orchestrator vetoes the skip if the frame is within six frames of a high-importance one, or if the previous frame scored above 0.5 and this one is still above 0.3. This keeps the encoder from punching holes in the middle of an action sequence.
  3. Final gate. The engine only actually drops if pressure is above 0.96 and the fused importance is below 0.25.
Design note

The layering is intentional and the effect is that dropping almost never happens. A compressor that thins footage during the busy moment defeats the purpose of the system, so the engine degrades quality first, at up to six CRF points, and only discards frames when the board is genuinely in trouble.

Quality tiers

The fused importance selects a CRF from four steps rather than mapping continuously. Discrete tiers are what keep the encoder from re-opening a segment on every frame.

Fused importanceCRFNominal fpsReads as
> 0.752024Subject in frame, moving, probably a face
> 0.502418Clear activity near the centre of the event
> 0.302812Peripheral movement, or the edges of the window
otherwise328Lead-in and lead-out padding

The fps column is computed and reported but not currently applied — the encoder runs at a fixed 24 fps and expresses quality through CRF alone.

Pressure is then added on top, and the result clamped to the range 18–40: 

d.crf = std::clamp(crfBase + (pressure * 6.0f), 18.0f, 40.0f);

Event clustering

Real incidents set off more than one detector. A door opening, a shout and movement across the lawn inside four seconds are one event, and writing three overlapping clips of it wastes storage and makes review harder. EventCluster merges them — but only when they are plausibly the same incident.

The two conditions

Two events merge if the gap between them is small and their triggers carry comparable weight.

Trigger containsWeight
door1.00
gunshot1.00
screaming0.95
glass0.90
anything unmatched0.50
motion0.40
grass0.20

Similarity is 1 - |weight_a - weight_b|, and merging requires it to exceed 0.55. A gunshot and a door (1.00 vs 1.00) merge freely; a gunshot and a grass overlap (1.00 vs 0.20, similarity 0.20) never do, however close together they land. The severity of an event is treated as a proxy for what kind of event it is.

The adaptive gap

The time window widens when things are busy: 

float density = std::min(3.0f, eventCountWindow / 8.0f);
return BASE_GAP * density;   // BASE_GAP = 120 frames = 5 s at 24 fps

Quiet periods use a tight window, so two unrelated events stay separate. A burst of detections widens it up to 15 seconds, on the reasoning that a lot happening at once is usually one thing happening.

Currently inert

Trigger strings do not reach the C++ side in the present build, so every event arrives weighted 0.50 and the semantic half of the merge rule cannot discriminate. The gap rule still works. Fixing the shared-memory handoff described in Architecture is what would switch this on.

Ranking

On flush, events are scored and sorted so the most important is encoded first — which matters if the queue is backed up and the ring is about to overwrite the frames. 

raw = 0.65f * triggerWeight
    + 0.25f * min(1.0f, clusterSize / 5.0f)
    + 0.10f * min(1.0f, (endFrame - startFrame) / 300.0f);

The encoder

H264Encoder is a wrapper around an FFmpeg process opened with popen. Frames are written to it as raw BGR24 over the pipe; FFmpeg does the colour conversion and the encoding. 

ffmpeg -y -loglevel error \
  -f rawvideo -pix_fmt bgr24 -s 640x360 -r 24 -i - \
  -c:v h264_v4l2m2m -b:v 2000k \
  -pix_fmt yuv420p /mnt/clipDrive/clips/iris_1234_1560_unknown.mp4

Hardware first, software second. The engine tries h264_v4l2m2m — the Pi's V4L2 memory-to-memory encoder, which offloads the work from the CPU entirely — and falls back to libx264 -preset veryfast when the pipe cannot be opened.

CRF to bitrate

The hardware encoder takes a target bitrate, not a quality factor, so the tier has to be translated: 

int bitrateKbps = 2000 - (crf - 18) * 80;
bitrateKbps = std::clamp(bitrateKbps, 500, 4000);

CRF 18 maps to 2,000 kbps and every point above it removes 80 kbps, giving 1,840 kbps at the top tier and 880 kbps at the bottom. The mapping is linear and approximate; CRF is a quality target and bitrate is a rate target, and they do not correspond exactly for any given scene.

Limitation

Because the bitrate is baked into the FFmpeg command line, changing it means closing and re-opening the pipe — which starts a new file. In the current build the encoder opens once per event, at the first frame's CRF, and per-frame quality decisions after that update the engine's internal state without reaching FFmpeg. Per-frame adaptivity is fully computed; what actually varies on disk is per-clip.

Output

Clips are written to /mnt/clipDrive/clips/, which StorageManager creates on startup if it is missing. The filename encodes the ring range and the trigger: 

iris_<startFrame>_<endFrame>_<trigger>.mp4

Each event logs a summary line on completion with the number of frames encoded, dropped and failed — failed meaning a slot that was empty, oversized, or held a JPEG that would not decode. A handful of failures at the edges of a window is normal and means the ring had already moved past those slots.
