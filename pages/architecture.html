01 · Architecture

Six processes, one buffer

Iris-Lite is not one program. It is six that agree on where the pixels live. Everything below follows from that: how they start, what they share, and what they refuse to send each other.

The processes

Each runs as its own OS process, launched by startIrisLite.sh in a separate terminal window. There is no supervisor and no restart logic — if one dies, the others keep running with a stale or missing input, which is a known weakness rather than a feature.

startCamera.py

Opens /dev/video0 through V4L2, forces MJPG at 1920×1080, and copies every frame into the iris_live_frame shared block. It also renders a live motion-diff overlay into the bottom-left 600×450 corner of the frame, which is a demo aid rather than part of the pipeline.

main.py

The buffer manager. Reads the live frame, re-encodes it as JPEG at quality 45, and writes it into a 7,200-slot ring at 24 fps. Also hosts the event bus listener and translates incoming event timestamps into ring indices.

detector_pipeline.py

The two-tier motion filter. A cheap always-on pass decides whether the expensive entropy-and-centroid pass is worth running.

zone_monitor.py

Segments a ground region once at startup, then watches for a foreground object's feet entering it and staying there.

listener.py

Gates on microphone volume, then classifies two-second windows of audio with a CNN trained for this project.

PerceptualCompressor

The C++ engine. Polls iris_concern_indices for a new frame range, then reads that range straight out of the ring, scores it and encodes it.

Why six

Python's GIL makes a single-process design pointless here: the three detectors are all CPU-bound OpenCV work and would serialise. Separate processes let the kernel put them on separate cores of the Pi's four, and let one detector crash without taking the camera down with it.

Shared memory

All coordination happens through POSIX shared memory. Python creates the blocks through multiprocessing.shared_memory; the C++ side attaches to the same names with shm_open and mmap, read-only.

BlockSizeWritten byContents
iris_live_frame 6.22 MB startCamera.py One raw BGR frame, 1920×1080×3. Overwritten in place every capture.
iris_frame_buffer_data 1.44 GB main.py The ring itself — 7,200 slots of 200,000 bytes, each holding one JPEG.
iris_frame_sizes 28.8 KB main.py Byte length of the JPEG in each slot, as uint32. A slot with size 0 is unwritten.
iris_frame_head_tail 16 B main.py Two uint64 ring pointers. The compressor reads head to know how far the writer has got.
iris_concern_indices 16 B main.py The current event window as a start and end ring index. This is the entire Python → C++ interface.
iris_indices 115.2 KB main.py Per-slot wall-clock timestamp and global frame counter. Populated but not currently consumed.
iris_lite_audio 19.2 MB listener.py A five-minute rolling audio ring at 16 kHz float32, kept for offline inspection.

Detectors attach their own read-only view of iris_live_frame rather than receiving copies. Adding a fourth detector therefore costs CPU but no extra memory, which is the main reason the design scales sideways at all on 2 GB.

Memory budget

The ring reserves 1.44 GB whether or not the slots are full, on a board with 2 GB total. Measured RSS across the whole system sits between 1.5 and 1.8 GB. There is no headroom for a second camera stream, and that constraint drives most of the resolution choices elsewhere in the system.

The ring buffer

main.py runs a fixed 24 fps loop. Each iteration it JPEG-encodes the current live frame at quality 45, and if that comes out larger than the 200 KB slot ceiling it retries at quality 30. If the frame still doesn't fit, it is skipped entirely — the loop would rather lose one frame than corrupt the slot boundary.

Head advances on every write. When head catches tail, tail is pushed forward too, so the oldest frame is silently dropped. At 24 fps over 7,200 slots the ring holds exactly five minutes. 

FPS               = 24
BUFFER_MINUTES    = 5
FRAME_BUFFER_SIZE = 24 * 60 * 5   # 7,200 slots
SLOT_SIZE         = 200_000       # bytes per slot

Storing JPEGs rather than raw frames is what makes the five-minute window affordable. Raw 1080p BGR would need 6.22 MB per frame, or roughly 45 GB for the same window. The cost is that the compressor has to decode every frame it wants to look at.

The event bus

Detectors talk to the buffer manager over a multiprocessing.connection socket on 127.0.0.1:8989, authenticated with a shared key. Nothing but a small record ever crosses it — no frames, no masks, no audio. 

@dataclass
class CaptureClass:
    startTime: str                    # "HH:MM:SS"
    endTime: str                      # "HH:MM:SS"
    trigger: str                      # e.g. "Gunshot (81.2%)"
    duration: Optional[float] = None
    isMotionSensor: Optional[bool] = None
    isDoorSensor: Optional[bool] = None

Keeping frames off the bus is deliberate. A detector that shipped its 640×360 working frame to the manager on every trigger would be moving about 700 KB per event through a Python pickle round-trip, and the manager already has the same pixels mapped. Sending timestamps instead reduces an event to a few hundred bytes.

From timestamp to frame index

Detectors know when something happened in wall-clock time. The compressor needs ring indices. main.py bridges the two by counting backwards from the current head at a known frame rate. 

padding_frames = 5 * FPS                              # 120 frames each side
start_offset   = int((now - start_ts) * FPS) + padding_frames
end_offset     = int((now - end_ts)   * FPS) - padding_frames

concern_indices[0] = (curr_head - max(0, start_offset)) % FRAME_BUFFER_SIZE
concern_indices[1] = (curr_head - max(0, end_offset))   % FRAME_BUFFER_SIZE

The five-second padding on each end is why a clip never opens mid-incident. Detectors already pad their own reported window by five seconds, so a ten-second trigger becomes a clip with roughly ten seconds of lead-in and lead-out around it — footage that was already sitting in the ring before anything noticed it was interesting.

Assumption

This arithmetic assumes the ring is filling at exactly 24 fps. If main.py falls behind — a slow JPEG encode, a skipped oversized frame — the mapping drifts, and the extracted window sits slightly later in time than the event actually was. The generous padding absorbs small drift; it does not fix it.

Handing off to C++

The compressor's main loop is a poll. It reads the two indices, compares them against the last pair it saw, and does nothing until they change. 

while (true) {
    uint64_t start = shared->startFrame;
    uint64_t end   = shared->endFrame;

    if ((start == 0 && end == 0) ||
        (start == lastStart && end == lastEnd)) {
        sleep_for(50ms);
        continue;
    }

    engine.enqueueEvent({ start, end, trigger });
}

A new pair is pushed onto an internal queue and a worker thread picks it up, so a second event arriving mid-encode is queued rather than dropped. The engine also refuses to read past the writer: before decoding slot i it checks the head pointer, and waits rather than reading a slot the camera loop hasn't filled yet.

Known gap

The C++ side expects the event block to carry a 64-byte trigger string alongside the two indices, but main.py only ever writes the indices. In the current build the trigger therefore arrives empty and the engine falls back to "unknown", which flattens EventCluster's trigger-weight model to its default and puts unknown in every clip filename. The detection metadata is carried correctly over the event bus — it just stops at main.py. See known issues.

Startup order

The launcher starts processes in a fixed sequence with sleeps between them, because several of them will exit immediately if their input block does not exist yet.

  1. main.py — creates every ring block, then blocks waiting for the live frame.
  2. startCamera.py — creates iris_live_frame. Given five seconds, since camera initialisation is the slowest step.
  3. detector_pipeline.py, listener.py, zone_monitor.py — each attaches to the live frame and raises OSError if it is missing.
  4. PerceptualCompressor — retries shm_open for up to 20 seconds before giving up.

startCamera.py unlinks any stale iris_live_frame before creating its own, so a hard kill of the previous run does not block the next one. The ring blocks have no such cleanup and are reattached if they already exist.
