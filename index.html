Overview

Iris_Lite is a developer‑grade intelligent camera system designed for the Raspberry Pi 4B. Instead of dumping raw footage to disk, it continuously captures 1080p frames into a shared memory buffer, then selectively compresses only the interesting segments based on a multi‑signal trigger pipeline.

The system is built around three core ideas:

  • Always‑on capture — a 5‑minute rolling buffer at 24 FPS stored in shared memory.
  • Event‑driven recording — motion, audio, zone overlap, and GPIO events decide when to save.
  • Importance‑aware compression — a C++ engine scores each frame and dynamically adjusts CRF.

The result is a camera that behaves more like a sensor fusion system than a dumb recorder—ideal for security, monitoring, or research setups where context matters more than raw uptime.

Key capabilities

  • 1080p MJPG ingest via V4L2 with real‑time overlays.
  • Shared memory frame buffer with timestamp indexing.
  • Motion detection using luminance shifts + CNT background subtraction.
  • Audio classification via TFLite (screams, glass, gunshots, etc.).
  • Zone‑based triggers using HSV grass segmentation + KNN background subtraction.
  • GPIO integration for door and motion sensors.

Design goals

  • Low overhead on Raspberry Pi 4B using hardware H.264 where possible.
  • Modular processes that can be debugged and replaced independently.
  • Deterministic behavior via explicit timestamps and shared memory indices.
  • Developer‑friendly Python + C++ codebase with clear separation of concerns.

System requirements

Hardware

  • Raspberry Pi 4B (2GB RAM or higher recommended).
  • USB camera supporting MJPG at 1920×1080 via V4L2.
  • USB microphone for audio classification.
  • GPIO sensors:
    • Door sensor on pin 17.
    • Motion sensor on pin 27.
  • Storage mounted at /clipDrive/clips/ (microSD or external drive).

Software

  • OS: Raspberry Pi OS (Bullseye or later, 64‑bit recommended).
  • Python: 3.12.7.
  • C++: GCC 11+ with C++20 (std::format support).
  • OpenCV: 4.x with bgsegm (via opencv-contrib-python).
  • FFmpeg: with h264_v4l2m2m hardware encoder support.
  • Python packages: opencv-contrib-python, numpy, pyaudio, ai-edge-litert, RPi.GPIO.
Note: On non‑Linux systems, GPIO is automatically disabled so you can still develop and test the rest of the pipeline without hardware sensors.

Getting started

1. Install dependencies

sudo apt update && sudo apt upgrade -y
sudo apt install -y ffmpeg libopencv-dev python3-pip cmake build-essential

pip3 install opencv-contrib-python numpy pyaudio ai-edge-litert RPi.GPIO

2. Clone and launch

git clone https://github.com/AbhiramV010/Iris_Lite.git
cd Iris_Lite
bash IRIS_Lite.sh

The launcher opens six uxterm windows and shows a loading bar while each process starts. All six processes must be running for the system to function correctly.

3. Configure storage

Ensure the clips directory exists and is writable: 

sudo mkdir -p /clipDrive/clips/
sudo chown <your-user> /clipDrive/clips/

Clips are saved as timestamped .mp4 files: 

iris_lite--YYYY-MM-DD_HH-MM-SS.mp4
Tip: Run the launcher from a regular Bash shell (not zsh) as IRIS_Lite.sh is written for Bash and assumes a POSIX‑style environment.

4. Typical dev workflow

Step 1 · Hardware sanity check
Verify the camera appears as /dev/video0 and the microphone is detected by ALSA.
Step 2 · Launch IRIS_Lite.sh
Confirm all six terminal windows show healthy logs (no repeated exceptions or shared memory errors).
Step 3 · Trigger events
Walk into frame, make noise, or toggle GPIO sensors and watch for capture events in the logs.
Step 4 · Inspect clips
Open the generated .mp4 files in /clipDrive/clips/ and verify quality vs. motion.

Architecture and data flow

Iris_Lite is composed of six parallel processes that communicate via POSIX shared memory and a socket‑based event bus on 127.0.0.1:8989. Each process has a single responsibility, which makes the system easier to reason about and debug.

High‑level pipeline

  • Capture: startCamera.py streams MJPG frames into shared memory.
  • Buffer: main.py maintains a 5‑minute rolling buffer of JPEG frames.
  • Triggers: detector_pipeline.py, listener.py, zone_monitor.py, and GPIO events emit CaptureClass objects.
  • Compression: C++ engine reads the relevant frame window and encodes to H.264 with dynamic CRF.

Core processes

  • startCamera.py Captures 1080p MJPG frames via V4L2 and writes them into a named shared memory block (iris_live_frame). It also renders a real‑time motion difference overlay on a configurable bottom‑left zone so you can visually confirm motion detection.
  • main.py Maintains a rolling 5‑minute buffer at 24 FPS (7,200 slots) using JPEG‑compressed frames (quality 25). It listens on the event bus for CaptureClass objects and maps timestamps to buffer indices for the C++ compression engine via the iris_concern_indices shared memory block.
  • detector_pipeline.py Runs a two‑tier trigger: luminance shift detection plus CNT background subtraction. Events that exceed an entropy threshold of 3.0 and show centroid movement over 50 consecutive frames send a CaptureClass with a ±5 second window around the event.
  • listener.py Samples audio at 16 kHz, builds mel spectrograms, and runs inference with a bundled TFLite model. It classifies:
    • Screaming
    • Gunshots
    • Glass breaking
    • Aggressive knocking
    • Car screech
    • Dog barking
    • Ambience
    Any concerning category triggers a capture with a configurable pre‑ and post‑event window.
  • zone_monitor.py Uses KNN background subtraction and HSV‑based grass segmentation to detect when a foreground object overlaps a defined ground zone. A capture is triggered after 2+ seconds of sustained overlap to avoid noise from transient artifacts.
  • sensor_helper.py Wraps GPIO access (door sensor on pin 17, motion sensor on pin 27). On non‑Linux systems, GPIO is automatically disabled for easier development. GPIO state is included in every CaptureClass.

CaptureClass payload

When any trigger fires, it emits a CaptureClass instance over the event bus. At a high level, this object contains:

  • start_time / end_time — timestamps defining the capture window.
  • trigger_type — e.g., "motion", "audio", "zone", "gpio".
  • importance_hint — optional hint for the compression engine (e.g., “high risk”).
  • gpio_state — door/motion sensor state at the time of the event.

main.py converts these timestamps into buffer indices and writes them into shared memory for the C++ compression engine to consume.

Compression pipeline (C++)

The C++ engine listens for events via the iris_concern_indices shared memory block written by main.py. On each event, it:

  • Extracts the relevant frame window from the shared buffer.
  • Scores each frame using ImportanceEngine:
    • Motion: 45%.
    • Edge density (Sobel): 35%.
    • Face detection (Haar cascade): 20%.
    computed at 320×180 resolution for efficiency.
  • Applies exponential smoothing: 0.85 * previous + 0.15 * raw to avoid erratic quality jumps.
  • Uses CompressionPolicy to:
    • Decide whether to drop a frame (importance + momentum vs threshold 0.55).
    • Compute a dynamic CRF in the range 16–36.
  • Streams kept frames to FFmpeg via pipe using h264_v4l2m2m on Linux, falling back to libx264 -preset ultrafast otherwise.

CRF segments are only re‑opened when the computed CRF shifts by ≥5 from the current value, reducing fragmentation and keeping clips clean and contiguous.

Troubleshooting

Camera not detected

Make sure the camera is visible as /dev/video0 and supports MJPG at 1920×1080: 

v4l2-ctl --list-formats-ext

If MJPG at 1080p is missing, lower the resolution or use a different camera.

Shared memory error on startup

If startCamera.py crashes, stale shared memory blocks may remain. Clear them with: 

python3 -c "from multiprocessing import shared_memory;
shared_memory.SharedMemory('iris_live_frame').unlink()"

Repeat for any other named blocks if necessary (e.g., iris_concern_indices).

Compression engine not encoding

Confirm the clips directory exists and FFmpeg supports the hardware encoder: 

ls /clipDrive/clips/
ffmpeg -codecs | grep h264_v4l2m2m

If the hardware encoder is missing, the engine will fall back to libx264, which is slower but still functional.

GPIO errors on non‑Linux systems

On non‑Linux platforms, sensor_helper.py automatically disables GPIO. This is expected during development on Windows or macOS and does not affect the rest of the pipeline.

Audio device not found

listener.py prefers USB or hardware audio devices, then falls back to the system default. List available devices with: 

arecord -l

If no devices are listed, check your microphone connection and ALSA configuration.
